01Основы тестирования и устройство вебаТребования, тест-кейсы и HTTP

В требованиях к учебному кабинету записано: «Зарегистрированный пользователь с верным паролем видит кабинет. При неверном пароле форма остаётся открытой и показывает ошибку». Так у тестировщика появляется критерий, по которому можно решить, правильно ли работает вход.

Превращаем требование в проверки

  • Позитивная проверка. Введите данные существующей учебной записи. Ожидаемый результат — заголовок «Личный кабинет».
  • Негативная проверка. Измените один символ пароля. Ожидаемый результат — сообщение об ошибке, доступ к кабинету закрыт.
  • Тест-кейс фиксирует предусловие, шаги, данные и ожидаемый результат. Чек-лист перечисляет проверки короче: верный пароль, неверный пароль, пустое поле, выход из кабинета.
  • Баг — расхождение между поведением и требованием. В баг-репорте запишите заголовок, версию и окружение, шаги, ожидание и факт. Приложите снимок экрана или ответ сервера, по которому коллега сможет воспроизвести ошибку.

Выбираем масштаб проверки

Модульный тест (unit) проверяет отдельную функцию, например удаление пробелов вокруг логина. Интеграционный проверяет взаимодействие частей, например сервиса входа с базой. Сквозной тест проходит весь путь от формы до кабинета. Эти уровни отвечают на вопрос «Какую часть системы проверяем?».

Функциональное тестирование сверяет поведение с требованиями. Дымовой набор (smoke) быстро проверяет жизненно важные функции новой сборки, включая вход. Регрессионный набор после изменений повторяет проверки уже работающих функций. Одна проверка входа может быть одновременно функциональной, сквозной и частью smoke-набора.

Прослеживаем запрос

Когда вы вводите адрес, браузер находит сервер по имени, устанавливает соединение и запрашивает страницу. Клиент отправляет HTTP-запрос с методом, путём, заголовками и, когда нужно, телом. Сервер отвечает кодом, заголовками и данными. HTTPS защищает обмен с помощью TLS. Откройте «Сеть» (Network) в инструментах разработчика, обновите страницу и найдите запрос документа.

GET получает ресурс, POST передаёт данные на обработку, PUT задаёт новое представление ресурса по известному адресу, DELETE удаляет ресурс. Код 200 означает успех, 400 — ошибочный запрос, 401 — требуется успешная аутентификация, 404 — ресурс не найден, 500 — внутренняя ошибка сервера. Для конкретного действия ожидаемый код берут из договора о работе API.

Практика

Представьте, что после ввода неверного пароля открывается кабинет. Составьте баг-репорт для разработчика. Проверьте себя: из записи понятно, что учётная запись существует, какой один шаг воспроизводит дефект и какой доступ был получен вопреки требованию.

02Python для тестовых данныхТипы, функции, файлы и классы

Создайте папку для упражнений. В этом уроке вы напишете модуль accounts.py, который понадобится в следующем. Правило учебного сервиса простое: «При сравнении логинов регистр и пробелы по краям не учитываются».

# accounts.py
def normalize_login(value):
    return value.strip().casefold()

if __name__ == "__main__":
    for raw in ["  MIRA ", "mira", "   "]:
        login = normalize_login(raw)
        if login:
            print(login)
        else:
            print("Пустой логин")

Запустите python accounts.py. Переменная raw по очереди указывает на три строки. Функция принимает аргумент value и возвращает обработанную строку. Пустая строка считается ложным значением в if. На экране появятся две строки mira и одна строка Пустой логин. Блок с __name__ позволяет импортировать функцию в тест без печати примеров.

Выбираем форму данных

Список ["mira", "anton"] хранит упорядоченный набор логинов, словарь {"login": "mira", "active": True} — поля одной записи, кортеж (" MIRA ", "mira") — неизменяемую пару входа и ожидания, множество {"admin", "reader"} — уникальные роли. Цикл for перебирает готовые данные. while повторяет действие, пока условие истинно. Например, после каждой попытки увеличить attempt на один и остановиться при attempt == 3.

Читаем файлы и разбираем ошибки

Модуль — файл Python с функциями или классами. В стандартной библиотеке json.load читает JSON-объекты и массивы, csv.DictReader читает строки CSV по названиям столбцов, xml.etree.ElementTree.parse разбирает дерево XML. Создайте рядом файл user.json с содержимым {"login": " MIRA "}. Сохраните этот пример в той же папке и запустите его из неё.

import json
from accounts import normalize_login

try:
    with open("user.json", encoding="utf-8") as source:
        user = json.load(source)
except FileNotFoundError:
    print("Создайте user.json рядом со скриптом")
except json.JSONDecodeError:
    print("Проверьте кавычки и запятые в JSON")
else:
    print(normalize_login(user["login"]))

try/except различает два конкретных сбоя подготовки данных. При корректном файле появится mira. Ошибка самого тестового утверждения должна оставаться видимой тому, кто запустил проверку.

Зачем автоматизатору ООП

Класс LoginPage описывает форму входа, объект LoginPage(browser) представляет её в конкретном браузере. Метод sign_in() скрывает поиск полей и нажатие кнопки — это инкапсуляция. Класс LoginPage(BasePage) может унаследовать общее действие открытия страницы. Если обычная и мобильная формы по-разному реализуют один метод sign_in(), тест может вызывать его одинаково — это полиморфизм.

03Первые автотесты в pytest и unittestФикстуры, параметры и отчёт о падении

Ожидаемое значение удобно записать прямо в программе. В папке с accounts.py создайте виртуальное окружение командой python -m venv .venv. В PowerShell активируйте его командой .\.venv\Scripts\Activate.ps1, в macOS или Linux — source .venv/bin/activate. Установите pytest командой python -m pip install pytest.

# test_accounts.py
import pytest
from accounts import normalize_login

@pytest.fixture
def account():
    return {"login": " Mira ", "active": True}

def test_active_account(account):
    assert account["active"]
    assert normalize_login(account["login"]) == "mira"

@pytest.mark.parametrize("raw, expected", [
    (" MIRA ", "mira"),
    ("An Ton", "an ton"),
    ("   ", ""),
])
def test_normalize_login(raw, expected):
    assert normalize_login(raw) == expected

Запустите python -m pytest -q test_accounts.py. pytest найдёт функции с префиксом test_. Фикстура передаст свежий словарь в первый тест. Параметризация создаст три отдельных случая из одной функции. Итог — четыре успешные проверки. Общие фикстуры одного набора можно вынести в conftest.py. Плагин pytest-xdist после установки добавляет параллельный запуск через -n 2; у параллельных тестов должны быть независимые данные.

Тот же контракт в стандартной библиотеке

# test_classic.py
import unittest
from accounts import normalize_login

class LoginTests(unittest.TestCase):
    def test_spaces_and_case(self):
        self.assertEqual(normalize_login(" MIRA "), "mira")

python -m unittest test_classic запустит один тест. Здесь проверки собраны в класс, а значения сравнивает метод assertEqual. При работе со старым проектом вы также встретите setUp и tearDown для подготовки и очистки перед каждым случаем и после него.

Практика

Временно уберите .strip() из функции и снова выполните команду pytest. Найдите в отчёте входную строку и различие между фактом и ожиданием. Проверьте себя: случай "An Ton" пройдёт, три других проверки упадут. Верните обработку пробелов и получите четыре успешных результата. Примеры параметризации в документации pytest

04Проверка формы в браузереSelenium, локаторы и ожидания

Selenium WebDriver управляет браузером. Автотест открывает страницу, находит элементы, выполняет действия и проверяет видимый результат. Построим локальный макет формы, чтобы результат зависел только от вашего кода. Сохраните этот текст в login.html рядом с тестами.

<!doctype html>
<meta charset="utf-8">
<label>Логин <input id="login"></label>
<label>Пароль <input id="password" type="password"></label>
<button id="submit">Войти</button>
<p id="result"></p>
<script>
  const field = id => document.getElementById(id);
  field("submit").onclick = () => {
    const ok = field("login").value === "mira"
      && field("password").value === "demo";
    field("result").textContent = ok ? "Личный кабинет" : "Ошибка входа";
  };
</script>

Для примера нужен установленный Chrome. Установите Selenium командой python -m pip install selenium; при первом запуске Selenium Manager может загрузить драйвер. Рядом с макетом сохраните файл test_ui.py.

from pathlib import Path
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

def test_login_opens_cabinet():
    url = Path(__file__).with_name("login.html").resolve().as_uri()
    with webdriver.Chrome() as browser:
        browser.get(url)
        browser.find_element(By.CSS_SELECTOR, "#login").send_keys("mira")
        browser.find_element(By.ID, "password").send_keys("demo")
        browser.find_element(By.XPATH, "//button[.='Войти']").click()
        result = (By.ID, "result")
        WebDriverWait(browser, 5).until(
            EC.text_to_be_present_in_element(result, "Личный кабинет")
        )

Команда python -m pytest -q test_ui.py откроет и закроет браузер. CSS-селектор #login находит элемент по идентификатору, XPath ищет кнопку с текстом. Явное ожидание даёт странице до пяти секунд показать результат и завершится раньше, как только условие выполнится. Для устойчивых локаторов выбирайте стабильные атрибуты или доступные имена элементов. Ожидания в Selenium

У Playwright есть Python API. Те же действия можно выразить как page.get_by_label("Логин").fill("mira") и page.get_by_role("button", name="Войти").click(). Cypress — ещё один браузерный инструмент, его тесты пишут на JavaScript или TypeScript. В Python-проекте сторонняя обёртка может запускать Cypress как отдельную команду; для записи самих сценариев на Python подходят Selenium и Playwright. Локаторы в Playwright · Документация Cypress

Практика

05Проверка API через RequestsКонтракт, статус ответа и данные

UI-тест видит результат на экране. API-тест обращается непосредственно к серверу и сверяет статус и поля ответа с контрактом. Допустим, клиент учебного банка ожидает получить баланс кошелька № 7 в копейках. Проверять один код 200 недостаточно: сервер может вернуть верный статус и ошибочную сумму.

Поднимаем учебный сервер

Создайте папку api_demo и сохраните в ней файл wallet.json с содержимым {"id": 7, "balance_kopecks": 12500, "currency": "RUB"}. Из родительской папки запустите python -m http.server 8765 --bind 127.0.0.1 --directory api_demo. Этот локальный сервер выдаёт подготовленный JSON по GET. Для теста откройте второй терминал в той же родительской папке и активируйте окружение.

# test_api.py
import pytest
import requests

@pytest.fixture
def base_url():
    return "http://127.0.0.1:8765"

def test_wallet_balance(base_url):
    reply = requests.get(f"{base_url}/wallet.json", timeout=3)
    assert reply.status_code == 200
    assert reply.headers["Content-Type"].startswith("application/json")
    wallet = reply.json()
    assert wallet["id"] == 7
    assert wallet["balance_kopecks"] == 12500
    assert wallet["currency"] == "RUB"

def test_missing_wallet(base_url):
    reply = requests.get(f"{base_url}/missing.json", timeout=3)
    assert reply.status_code == 404

Выполните python -m pip install requests pytest и python -m pytest -q test_api.py. Пройдут два теста. В серверном терминале будут видны пути и коды обоих запросов. По окончании нажмите там Ctrl+C.

Для организации API-тестов иногда используют плагины семейства pytest-requests. Здесь ту же задачу решает связка pytest, Requests и фикстур: адрес сервера хранится в одном месте, ожидания остаются в конкретных тестах. Для API, которое принимает новые записи, requests.post(url, json=fields, timeout=3) отправит JSON. Методы requests.put и requests.delete пригодятся для замены и удаления записи. Коды и итоговое состояние проверяйте по контракту настоящего сервиса. Запросы и ответы в Requests

SQL и проверка записи из Python

В SQL команда INSERT добавляет данные, SELECT выбирает столбцы, WHERE задаёт условие, JOIN связывает строки таблиц по ключу. Сохраните и запустите пример: SQLite создаст отдельную базу в памяти на время упражнения.

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE users (id INTEGER PRIMARY KEY, login TEXT);
    CREATE TABLE wallets (user_id INTEGER, kopecks INTEGER);
    INSERT INTO users VALUES (7, 'mira');
    INSERT INTO wallets VALUES (7, 12500);
""")
row = db.execute("""
    SELECT users.login, wallets.kopecks
    FROM users JOIN wallets ON users.id = wallets.user_id
    WHERE users.login = ?
""", ("mira",)).fetchone()
assert row == ("mira", 12500)
print(row)
db.close()

В результате появится ('mira', 12500). Замените значение параметра на "anton". Теперь fetchone() вернёт None: подходящей строки нет. Параметр ? позволяет передать логин отдельно от текста SQL.

Воспроизводимое окружение в Docker

Контейнер запускает тест с выбранной версией Python и своими зависимостями. При установленном Docker сохраните рядом с модулем файл Dockerfile:

FROM python:3.12-slim
WORKDIR /tests
COPY accounts.py test_accounts.py ./
RUN python -m pip install pytest
CMD ["python", "-m", "pytest", "-q", "test_accounts.py"]

Соберите образ командой docker build -t qa-evening . и запустите docker run --rm qa-evening. В результатах будут те же четыре успешные проверки. В командном проекте зафиксируйте проверенные версии зависимостей.

От отчёта до CI/CD

Установите allure-pytest командой python -m pip install allure-pytest. Запуск python -m pytest test_accounts.py --alluredir=allure-results запишет данные для отчёта. Если установлена утилита Allure Report 2, allure serve allure-results откроет отчёт: выберите случай и посмотрите входные данные и утверждение. Настройка Allure для pytest

CI запускает такие проверки по событию в репозитории. На GitHub сохраните этот файл как .github/workflows/qa.yml и отправьте его вместе с Dockerfile, модулем и тестами:

name: QA
on: [push, pull_request]
jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t qa-evening .
      - run: docker run --rm qa-evening

Во вкладке Actions появится запуск для отправленного изменения. Падение pytest вернёт ненулевой код, и шаг CI получит статус ошибки. В Jenkins те же команды выполняют в этапах сборки и тестирования. Для ночной регрессии задают запуск по расписанию. В процессе CD успешные проверки могут быть условием перехода к доставке или развёртыванию новой версии.
