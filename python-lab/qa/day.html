09:30 · Проверяем вход

По требованию после входа клиент видит заголовок «Личный кабинет». Аккаунт уже создан. UI-тест повторяет действия пользователя в браузере. Для мобильного приложения принцип тот же, но нужен драйвер или инструмент для выбранной платформы.

# Фрагмент теста Playwright. page — страница тестового браузера.
page.goto(base_url + "/login")
page.get_by_label("Логин").fill(user.login)
page.get_by_label("Пароль").fill(user.password)
page.get_by_role("button", name="Войти").click()

Какое утверждение проверит нужный результат?

  • Кнопка «Войти» была доступна перед нажатием.

    Кнопка могла быть доступна даже при сломанном входе. Выберите признак успешного входа, который видит клиент.

  • После нажатия появился заголовок «Личный кабинет».

    Добавьте expect(page.get_by_role("heading", name="Личный кабинет")).to_be_visible(). Эта проверка Playwright дождётся появления заголовка в пределах тайм-аута и упадёт, если кабинет не откроется.

  • Через две секунды после клика браузер всё ещё открыт.

    Браузер остаётся открытым и на странице ошибки. Пауза не проверяет требование, а на медленном стенде ещё и сделает тест нестабильным.

10:15 · Проверяем баланс через API

Сервер отдаёт данные кабинету по HTTP. Подготовленный счёт QA-17 содержит 1250 рублей. По контракту API передаёт баланс в копейках, валюта — RUB. Токен и адрес тестового сервера выдаёт фикстура.

response = requests.get(
    base_url + "/api/accounts/QA-17",
    headers={"Authorization": f"Bearer {token}"},
    timeout=5,
)
# Эталон для этого счёта: 125000 копеек.

Какая проверка обнаружит, что сервер перепутал рубли с копейками?

  • Проверить только статус 200.

    Статус 200 означает, что сервер обработал запрос. Баланс в успешном ответе всё равно может оказаться неверным.

  • Принять любое число больше нуля.

    Числа 1250 и 125000 положительные. Чтобы заметить ошибку в единицах измерения, сравните ответ с известной суммой на подготовленном счёте.

  • Проверить статус, точную сумму в копейках и валюту.

    Сначала выполните assert response.status_code == 200. Затем прочитайте body = response.json() и отдельно проверьте body["balance_minor"] == 125000 и body["currency"] == "RUB" с помощью assert. Так в отчёте видно, какая часть контракта нарушена.

11:30 · Готовим набор тестов к росту

В проекте появились тесты пополнения и списания. По отдельности они проходят, а при параллельном запуске иногда видят чужие изменения баланса. Команда использует pytest и хочет легко добавлять новые проверки.

tests/
  conftest.py        # общие фикстуры
  test_account.py    # проверки API
  test_login.py      # сценарии входа

Как изменить тестовый фреймворк, чтобы тесты не портили данные друг друга?

  • Выдавать каждому тесту отдельный счёт через фикстуру.

    Фикстура в conftest.py создаёт уникальный счёт перед тестом, передаёт его через yield и очищает после теста. Тест запрашивает фикстуру по имени аргумента. К изолированным тестам можно подключить pytest-xdist для параллельного запуска и allure-pytest для сбора результатов.

  • Добавить случайную задержку перед каждым списанием.

    Задержка изменит порядок запросов, но у тестов останется общий счёт. Подумайте, как дать каждой проверке собственные данные.

  • Копировать один номер счёта во все новые файлы тестов.

    Разные файлы продолжат обращаться к одному объекту на сервере. Значение счёта должно отличаться у одновременно работающих тестов.

13:40 · Разбираем падение API-теста

После обновления кодовой базы CI запустил сотни тестов. Откройте в отчёте первую ошибку. Вы повторили запрос вручную на том же стенде, подтвердили исходную сумму счёта и получили тот же ответ.

Стенд: staging · сборка 418 · счёт QA-17
GET /api/accounts/QA-17 → 200
Ожидалось: balance_minor = 125000
Получено:  balance_minor = 1250

Что передать разработчику?

  • Предложить изменить ожидаемую сумму теста на 1250.

    Так тест зафиксирует ошибочный ответ как норму. Требование и начальные данные подтверждают сумму в 125000 копеек.

  • Баг-репорт с условиями, шагами, ожидаемым и фактическим результатами.

    Заголовок: «API кабинета возвращает 1250 копеек вместо 125000 для счёта с 1250 рублями». Укажите стенд и сборку, создание счёта с эталонным балансом, метод и путь запроса. Приложите обезличенный ответ и ссылку на запуск без токена авторизации.

  • Сообщить только, что сборка красная.

    По цвету сборки нельзя воспроизвести дефект. Разработчику нужны исходные данные, запрос и расхождение с контрактом.

15:10 · Разбираем падение UI-теста

Второй тест упал при поиске кнопки. Вы открыли страницу вручную: кнопка переехала в другой блок, сохранила имя «Войти» и видна пользователю. С валидными данными кабинет открывается. В отчёте остался старый селектор.

TimeoutError: locator(".sidebar .green-button")
Снимок страницы: <button type="submit">Войти</button>

Как восстановить проверку и сохранить её смысл?

  • Завести баг «Вход недоступен» по одному тайм-ауту.

    Ручная проверка подтвердила, что вход работает. Ошибка указывает на поиск элемента по прежней разметке.

    При следующем изменении команда пропустит настоящий дефект. В сценарии устарел способ поиска кнопки.

  • Найти кнопку по роли и имени, повторить тест и проверить открытие кабинета.

    Обновите клик на page.get_by_role("button", name="Войти").click(). Оставьте проверку заголовка кабинета. Повторный запуск покажет, что тест снова проверяет вход после изменения вёрстки.

16:45 · Включаем автоматический запуск

Разработчики открывают запросы на слияние несколько раз в день. Быстрые тесты входа и баланса занимают минуту, полная регрессия — сорок минут. Команде нужны быстрый сигнал перед слиянием и полный утренний отчёт.

Быстрые тесты: pytest -m smoke
Весь набор:    pytest
Отчёт:        результаты и логи конкретной сборки

Как организовать процесс в GitHub Actions или Jenkins?

  • Запускать smoke при изменениях в запросе на слияние, всю регрессию — ночью по расписанию.

    CI поднимает воспроизводимое окружение, например Docker-контейнер с зависимостями и браузером. Он запускает pytest и сохраняет отчёт даже при падении. Утром команда открывает результаты нужной сборки, а автор изменения видит быстрый результат до слияния.

  • Отправлять напоминание о ручном запуске раз в неделю.

    Между двумя запусками накопится много изменений. Нужны события, по которым CI сам запустит нужный набор.

  • Запускать все тесты по просьбе автора после слияния.

    Обратная связь придёт после объединения кода. Сопоставьте быстрый набор с запросом на слияние и выберите отдельное время для длинного прогона.
